# OpenManus ZIP compliance audit — review branch

**Baseline:** `90c784c1da876014145d9df46f9727d146bdc20e` on `main` (2026-10-01). **Status:** corrective changes under review; **not a complete ZIP implementation or laptop-verified release**. No changes from this audit have been merged to `main` yet.

This assessment is based on every member of the user-supplied `Downloads.zip`: `New update.docx`, `OpenManus Multi-Model Capability Update.docx`, `OpenManus capabilities categorized into eight categories.docx`, `SKILL (4).md`, `SKILL (5).md`, `SKILL (6).md`, `SKILL (7).md`, `emil-design-eng_SKILL.md`, `sleek-design-mobile-apps_SKILL.md`, and `ui-ux-pro-max_SKILL.md`. DOCX paragraphs and table cells were extracted and read in source order. The blueprint's *illustrative* capability IDs do not always match the authoritative 1–400 inventory (for example, the example labels “Create web applications” as 48 while the inventory places it at 11); use the numbered inventory as the source of truth. `SKILL (4).md` and `SKILL (5).md` are duplicate frontend-design guidance. Taste, Impeccable, and UI/UX Pro Max refer to external script/reference resources **not included** in the ZIP, and Sleek's optional external Pro API is not part of the zero-cost local default. The repository's local design playbook normalizes the available guidance; it does **not** magically install those missing tools.

## Actual path of a user message

1. The browser sends the original composer text and **explicit current-message attachment IDs** to `POST /api/projects/{project_id}/chat`. It rejects only all-whitespace input client-side. Server-side auth, input bounds, project ownership, attachment validation, and idempotent replay still run before a new controller call; these **must remain**, as the ZIP explicitly requires platform safety. A replayed idempotency key returns its saved request rather than calling a model a second time.
2. `runtime/app/api/routes.py` gives a newly accepted message to `make_authoritative_plan` in `runtime/app/platform/reasoning.py`. There is no pre-DeepSeek greeting, math, build, task/conversation keyword classifier, or user-selectable mode. DeepSeek first chooses `respond` or `execute` from a compact prompt. This is a **model-owned choice**, not a pre-model route filter.
3. A `respond` result is answered by DeepSeek and streamed. For `execute`, the same model sees the local registry subset with runnable handlers, selects ordered IDs and their owners, and the platform checks IDs, model availability, dependency order, permissions, and output integrity. This validation is **after** DeepSeek's decision, not a deterministic intent classifier.
4. In `AgentOrchestrator`, selected image work goes to Gemma, research to Qwen2.5 3B with retrieved sources, design to Llama 3.2 3B, coding to Qwen Coder, and required user actions pause the workflow. Direct `/api/tasks`, active-task follow-ups, and scheduled prompts also use the DeepSeek controller. A selected unavailable specialist fails instead of silently switching models.

## Review-branch changes and verification

This branch removes stale image auto-selection, restores user authorization on remote Git actions, scopes the agent's GitHub tool, requires matching action evidence before declaring a selected Git operation complete, passes actual visual-reference/research context to Llama, rejects malformed specialist output, removes a false research-success fallback, gives DeepSeek the user-handoff wording, labels user replies honestly, makes model health check exact tags, and adds a **read-only, sequential, local-only** Docker probe. Regression coverage includes multiple current images, old-image isolation, malformed specialist output, explicit Git permission and result evidence, exact model tags, model-to-model provenance, and user-pause wording. Tests here use controlled stand-ins; they are **not five real Ollama model calls**.

Sandbox verification: **198 runtime tests passed** (`pytest -q --ignore=tests/sandbox`), Python compilation and JavaScript syntax checks passed, registry JSON parsed, `git diff --check` passed, and headless Chromium displayed the acknowledged—not “verified”—user action label. Docker-dependent tests and any actual laptop model, memory, browser-preview, or remote GitHub scenario were **not run** here.

Run the probe **after** configuring and pulling the five model tags on the Windows Ollama host and starting the rebuilt container:

```powershell
docker exec openmanus python -m deploy.check_multimodel
```

It prints only readiness, pass/fail and elapsed time; a nonzero exit means the five-role/greeting gate failed. The ZIP then requires a real current-image → sourced research → Llama design → Qwen build/preview → Gemma/Llama review → authorized GitHub workflow, along with SQLite-restart and 16 GB memory/latency tests on the laptop. Neither this script nor mocked pytest can assert those outcomes in advance.

**Release decision:** keep this work on the review branch until the real model probe and complex laptop scenario pass, and until the generic 400-entry registry claims have per-capability verifiers or are plainly labeled inventory-only. The previously granted main-branch authorization remains, but pushing *untested “full compliance”* to main would repeat the failure this audit is meant to prevent.
